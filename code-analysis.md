# llfile Code Analysis — Bugs & Refactoring Opportunities

Synthesized from 8 parallel review passes covering the full `llfile/` source tree (core dispatch, directory traversal, copy/move/delete, compare/find/size, dir listing/replace, printf/exec/info, llsupport.cpp, and misc utility modules). Most severe first.

> Updated 2026-07-19: re-checked against the current working tree, which has uncommitted edits to `llprintf.cpp`/`llsupport.cpp` since this file was first written. Findings below are annotated `[FIXED]`, `[PARTIALLY FIXED — new bug]`, or `[REGRESSED]` where the working tree has moved since the original pass; everything else was spot-checked at its cited line and still applies as written.

## Critical (crash / memory-safety / security)

1. **[FIXED]** Stack buffer overflow, user-triggerable — `llsupport.cpp:326-334` `ReplaceDstWithSrc()`: a destination pattern with 10+ consecutive `#` (e.g. `file##########.txt`) did an unbounded `sprintf` into `char numBuf[10]`. An earlier working-tree edit clamped only the `sprintf` width but still passed the unclamped `digits` count to `ReplaceString(dstFile, dstIdx, remLen, numBuf, digits)`, which forwards it into `std::string::replace(offset, removeLen, addStr, addLen)` — that left an OOB *read* past `numBuf` for 10+ `#` patterns. Now fixed by clamping `digits` itself once (`digits = min(digits, (unsigned)(sizeof(numBuf) - 1))`) before both the `sprintf` call and the `ReplaceString` call, so the two can no longer disagree — the destination pattern silently caps at 9 digits instead of overflowing or over-reading. `llexec -c` (llexec.cpp:323-326) calls the same `ReplaceDstWithSrc()` directly, so it's covered by this fix too.
2. **Command injection in `llexec`** — llexec.cpp: default command is `cmd /c echo ...`; matched filenames are appended with only optional quoting (`-Q`, off by default). `cmd.exe` treats `&`, `|`, `<`, `>` as separators regardless of quoting, so a file/dir named e.g. `x & calc.exe & y.txt` anywhere in a scanned tree executes attacker content.
3. **[FIXED]** NULL-deref crash in `llexec -C=0` — llexec.cpp:235-244: `m_pPattern` was never set on this path, so combining `-C=0` with a `*` in the command template crashed in `strrchr(NULL, ...)` inside `ReplaceDstStarWithSrc()`. Fixed two ways: (a) the `-C=0` branch in llexec.cpp now sets `m_pPattern = (argc > 0) ? pDirs[0] : ""` before calling `ProcessEntry()`, so it's never NULL there; (b) `ReplaceDstStarWithSrc()` in llsupport.cpp now defends against `pPattern == NULL` at the top (`if (pPattern == NULL) pPattern = "";`) as a root-cause backstop for any other caller. Also zeroed the synthetic `WIN32_FIND_DATA data` in that same `-C=0` branch (`ClearMemory(&data, sizeof(data))`) — `cFileName` was previously left uninitialized stack garbage, which `FilterDir()`/`LLBase::FilterDir` reads via `LLPath::Join(pDir, pFileData->cFileName)` to build `m_srcPath`.
4. **[FIXED]** Use-after-free in `RunCommands` — llsupport.cpp:2061-2123: `Close()` deleted the `PROCESS_INFORMATION` but left the dangling pointer in `m_processList`; `GetExitCode()` then read through the freed pointer (and, independently, always got `exitCode = -1` because `Close()` had already set `hProcess = INVALID_HANDLE_VALUE` before the read); `Clear()`'s `for` loop erased from the list itself after `Close()` had already erased the same node, corrupting the iterator and skipping every other tracked process. Fixed: `Close()` now erases its own entry from `m_processList` (in addition to deleting it), so the list never holds a stale pointer; `GetExitCode()` now calls `GetExitCodeProcess()` *before* `Close()` instead of after, so it reads a live handle's real exit code instead of a freed pointer / `INVALID_HANDLE_VALUE`; `Clear()` now advances its iterator to the next node *before* calling `Close()` (which erases the current node), which is safe for `std::list` since erasing one node never invalidates other iterators — no more double-erase, no more skipped entries.
5. **[FIXED]** Heap corruption in directory sort — lldirSort.cpp: `SetSort()` computes each pooled `LLDirEntry`'s allocation size (`m_ourSize`, ~line 490) from `m_values`, and `case 'n'/'e'/'p'/'t'` (name/ext/path/type sort without `needAllData`) set `m_values = 0` — zero bytes reserved for `lvalue[]` — since those sorts compare via `CompareDataNameInc`/`CompareDataExtInc`/etc. and never touch `lvalue[]` at all. But all four of those cases also point `m_fillEntryData`/`m_fillFindData` at `FillEntryMtime`/`FillFindDataMtime` (reused as a generic "copy extra display fields" helper) — and those two functions unconditionally wrote/read `dirEntry.lvalue[0].ft` before ever checking `m_values`, so every scanned entry under a name/ext/path/type sort (without `-a` for "all data") wrote 8 bytes of FILETIME past its allocation, into the next pooled entry. (`FillEntryAtime`/`Ctime`/`FillEntrySize` don't have this problem — their sort types (`'a'`,`'c'`,`'s'`) set `m_values = needAllData ? 4 : 1`, never 0, so their `lvalue[0]` write always lands in an allocated slot.) Fixed by guarding the `lvalue[0]` read/write in `FillEntryMtime`/`FillFindDataMtime` with `if (dirSort.m_values != 0)`, so it's skipped entirely when nothing was allocated, and still runs for the `m_values==1` case (plain `-m` sort) where `lvalue[0]` is the actual, correctly-allocated sort key. Also loosened the `assert(m_values == 0 || m_values == 4)` in both functions to include `== 1`, since `case 'm'` legitimately produces `m_values==1` and the old assert would fire on that valid path.
6. **[FIXED]** In-place replace truncates/corrupts the file being edited — llreplace.cpp:1352-1503: `-g=Ui` (`OpenOutput()`, ~line 1464-1503) opened `m_srcPath` itself for output (`out.open(m_srcPath, ...)`) while a second handle onto the same path was still being read — an `ifstream` in the by-line path, or an active `MemMapFile` view in the mmap path. Opening for `std::ios::out` without `app`/`ate` truncates the file immediately, so the moment the first match was found the file's on-disk contents were destroyed out from under the still-open reader: the by-line path lost everything after the first match (subsequent `getline(in, ...)` calls hit a now-truncated file), and the mmap path was worse — truncating a file while its pages are still mapped and being read by `regex_replace()` risks an in-page I/O structured exception, which the `catch (...)` block may not even catch. The `'b'` (backup) mode already avoided this by writing to a `_tmp_XXXXXX` temp file and renaming it over `m_srcPath` afterward via `BackupAndRenameFile()`; `'i'` mode just skipped that by setting `m_tmpOutFilename = m_srcPath` and writing straight into it. Fixed by making `OpenOutput()` always write to a temp file (removing the `'i'`-vs-`'b'` branch and the now-unneeded `out.seekp(inPos)`), so `m_tmpOutFilename != m_srcPath` is now always true and `BackupAndRenameFile()`'s existing `MoveFileEx(...)` rename-over-original logic — previously only exercised by `'b'` mode — now runs for `'i'` mode too, once `in`/`mapFile` are closed and reading is fully done.
7. **[FIXED]** Non-deterministic comparator can drop files from listings — lldirSort.cpp:62-77 `CompareDataExtInc()`: extensionless files (`Makefile`, `README`) were compared by raw pointer address (`(size_t)pLeftExt & 0x8fff`), breaking strict-weak-ordering; the manual linked-list insertion sort (lldirSort.cpp:297-360) relies on that ordering being consistent/transitive to pick a scan direction and guarantee an insertion point is found, so an inconsistent comparator could let a node fall through both the front-scan and back-scan without ever being linked in — silently dropping it from the listing. Fixed by making the no-extension case deterministic: entries with no extension now sort before entries with one, and two extensionless entries fall back to `CompareDataNameInc()` (full-name comparison) — no more pointer-address comparisons. Added a forward declaration of `CompareDataNameInc()` since it's defined later in the file.
8. **[FIXED]** `llcmp` OOB read / divide-by-zero / OOB write — llcmp.cpp:
   - `cmpList[0]` (llcmp.cpp:1478, in the `DoCmp()` grouping loop): if the *first* file in a same-name group failed the `-X=`/include/rhs filters, it was never pushed to `cmpList`, leaving it empty — the loop's `while (... && cmpMatch(pDirEntry, cmpList[0], m_levels))` condition then indexed an empty vector (UB/crash). Fixed by capturing the group's anchor entry (`pGroupFirst`) *before* filtering and using that for the `cmpMatch()` grouping check instead of `cmpList[0]`; also skip to the next group via `continue` when `cmpList` ends up empty (the whole group got filtered out) rather than calling `CompareFileSpecs`/`CompareFileData` — those already tolerate an empty list (return `sIgnore`), but there's nothing to do so no need to call them.
   - `whereSize = DWORD(fileSize2 / 100)` (llcmp.cpp:678 and again at the display site, ~1002): truncates to 0 for any file under 100 bytes, and `compareInfo.whereCnt[differAt/whereSize]++` then divides by zero. Fixed by clamping `whereSize` to a minimum of 1 at both sites.
   - Same `whereSize` truncation also let `differAt/whereSize` exceed index 99 for files whose size isn't an exact multiple of 100 (e.g. 105 bytes → `whereSize=1`, `differAt` up to 104 → index 104 into `whereCnt[100]`) — an OOB **write** past the array, not just a display artifact. Fixed by clamping the computed bucket index to `ARRAYSIZE(whereCnt)-1`.
   - `differAt*100/fileSize1` and `diffCnt*100/fileSize1` (llcmp.cpp:991, 995): divide-by-zero when `fileSize1==0` (an empty file compared against a non-empty one takes the size-mismatch path, so `differAt` is never set by the byte-compare loop, but the percentage is still computed on display). Fixed with a `fileSize1 != 0 ? ... : 0` guard at both sites.
9. **`llsize` command is dead** — llsize.cpp:764-836: `Run()` never scans directories and `ProcessEntry` unconditionally `return sIgnore` — passing any file/dir args to `llsize` does nothing; it just dumps disk info.
10. **[FIXED]** Multi-dir watch races/leaks — lldir.cpp:1445-1471 `WatchDir()`: allocated `MonitorDirInfo[argc]` (one slot meant per watched directory) but the setup loop wrote through the bare `pDirInfo` pointer (always element 0) instead of `pDirInfo[argIdx]`, and passed that same base pointer to every `CreateThread()` call — so all `argc` threads shared one `MonitorDirInfo` instance instead of each getting its own. That meant `dir` was overwritten on every loop iteration (readers on other threads could race to see whichever value happened to be there, generally ending up watching the last directory in the list rather than their assigned one), `count++` in `MonitorDirThread()` (line ~1402) was an unsynchronized read-modify-write shared across every thread, and one thread's watch-limit hit set a shared `abort` flag that silently killed every other thread's watch loop too. Separately, `pThread`/`pThreadId`/`pDirInfo` were all `new[]`'d but never freed, and the `HANDLE`s in `pThread[]` were never `CloseHandle()`'d. Fixed by indexing `pDirInfo[argIdx]` in the setup loop and passing `&pDirInfo[argIdx]` to `CreateThread()` so each thread gets its own independent struct, and by closing each thread handle and `delete[]`-ing all three arrays after `WaitForMultipleObjects(..., true, INFINITE)` returns (safe there since that call only returns once every thread has exited and is no longer touching `pDirInfo[]`).
11. **[FIXED]** Symlink/junction cycles cause stack overflow — dirscan.cpp: `m_skipJunction` defaulted `false` and there was no visited-dir tracking or depth bound, so a self-referential junction/symlink with `-r` recursed through `GetFilesInDirectory()`/`GetFilesInDirectory2()` forever, overflowing the stack. Fixed two ways: (a) `DirectoryScan`'s constructor (dirscan.cpp:241) now defaults `m_skipJunction(true)`, matching the safe convention `lldel.cpp` already opted into on its own (`m_skipJunction = true` at lldel.cpp:159, with a `-j` flag to opt back into following junctions) — every other command built on `DirectoryScan` now skips reparse points by default too, so cycles can't form via junctions/symlinks in the first place. This is a behavior change: commands that used to silently follow junctions (and could double-count or infinite-loop on cycles) now skip them unless the caller explicitly sets `m_skipJunction = false`. (b) As an unconditional backstop independent of that setting, `GetFilesInDirectory2()` (dirscan.cpp:303-312) now checks `depth` against a hard `sMaxRecurseDepth = 512` at entry and bails out with an error message instead of recursing further — covers any other cycle-forming path (e.g. `m_skipJunction` explicitly disabled) that isn't a reparse point.
12. **[FIXED]** `SharePtr::operator=` leaks — SharePtr.h:54-61: reassignment overwrote `m_pShareItem` with the new (ref-counted) value from `rhs` without ever releasing the previously-held `ShareItem` — if `this` held the last reference, that `ShareItem` (and the `T*` it wraps, via `~ShareItem()`'s `delete m_pItem`) leaked permanently since nothing else would ever call `Dec()`/`delete` on it. Fixed by capturing the old `m_pShareItem` in a local (`pOld`), assigning the new one first (mirroring the copy-ctor's `Add()`), then releasing `pOld` afterward — decrementing its ref count and deleting it if it reaches 0 — same pattern as the destructor. Note: `Clear()` (line 110-111) has the same underlying bug (nulls `m_pShareItem` without releasing it) but wasn't named in this issue, so it was left as-is — flag if you want that fixed too.

## Correctness bugs (no crash, wrong behavior)

- `llmove.cpp:499` — clears read-only using the **destination's** old attributes instead of the **source's** (copy-paste of `srcFileInfo`→`dstFileInfo`), so force-move of a read-only file can leave a stray copy behind.
- `-o` (older-only) alone can never actually overwrite in llcopy/llmove — sequential `if`s instead of else-if (llcopy.cpp:442-448, llmove.cpp:375-381).
- `llfind -E=s` returns the last file's size, not the accumulated total, and truncates to 32-bit `int` (llfind.cpp:350-352).
- `llcmp -t` (text mode) reports files with appended/extra trailing content as equal — comparison loop stops at the shorter file (llcmp.cpp:781-808).
- `llcmp` bypasses the shared `FilterDir()` and reimplements filtering 3x inline, silently ignoring `-T`/`-P=` that work fine in `llfind` (llcmp.cpp).
- `llprintf`: `\g` prints `<` instead of `>` (missing `break`, fall-through case), `%o` prints hex not octal, precision (`%.3s`, `%.5d`) is silently a no-op, `new[]`/`delete` mismatch on every formatted directive, `PrintFile()`'s match counter never increments so `-Q=n` accounting is inconsistent between input modes, file sizes ≥4GB truncate/wrap.
- `llprintf.cpp` **[FIXED in working tree]** `-e=*`/`-e=<envName>` env-listing (`case 'e'`, ~line 1057) and the main input-list filter (~line 1275) both called `PatternListMatches(...)` **negated** (`!LLSup::PatternListMatches(...)`), so `-P=<pattern>` was inverted — it excluded matches and kept everything else. Both sites now call it unnegated and match correctly. Help text typo `-p%s\n` → `-p=%s\n` also fixed.
- `llprintf.cpp` **[FIXED]** `case 'p'` (~line 1142-1169): when `inList` is empty, the call to `PrintFormatted(m_printFmt, inList, ++nLine)` that prints a bare message (`p -p="hello world\n"`) was commented out again (line 1158), with a stale comment above it still claiming "you can use it to present a message, like p -p='hello world'" — the exact behavior commit `5984dc6` ("restore print (p) command support for no inputs...") had added, regressed back to dead code. Fixed by uncommenting the `PrintFormatted()` call and replacing the stale comment with one describing the current behavior. The `argc==1`/no-`-p` fallback lower down (line 1261, `p "hello world"` with no `-p=` flag at all) is a separate code path and was untouched.
- `llinfo`: unchecked `CreateFileMapping`/`MapViewOfFile` → crash on a bad PE file kills the whole scan; unchecked `e_lfanew` → OOB read on malformed headers; `okay=true` set outside the per-key success check makes "has version info" a false positive.
- `llsupport.cpp` `FileTimeDifference`: signed `delta` divided by unsigned `resolution` turns "destination is older" into a huge positive number instead of negative — this feeds directly into copy/move's `-o`/age logic.
- `llsupport.cpp` `RunCommand` timeout: reports the literal `WAIT_TIMEOUT` (258) as if it were the process's real exit code, and never terminates the hung child.
- `llmsg.cpp` `RedirectOutput` tee mode (`-3=<file>`) constructs a tee stream and never installs it — the tee feature is a no-op; `GetErrorMsg` can resize a string by `(size_t)-1` and throw when a formatted error has no `\r`.
- `llfile.cpp:431,405,440` — three unchecked `strcpy`s into fixed stack buffers from argv-derived paths (real overflow if a path is long enough).
- `MemMapFile`/`Handle.h`: `Handle::IsValid()` only checks `INVALID_HANDLE_VALUE`, but `CreateFileMappingW` fails with `NULL` — a failed mapping is reported as a successful `Open()`.
- `Security.cpp::RemoveFile` — doesn't check `GetFileAttributes` for `INVALID_FILE_ATTRIBUTES` before testing the read-only bit.
- `llstring.cpp` `isspace(*pSrc)` on a signed `char` — UB/assert on extended-ASCII bytes in filenames; `PadLeft`/`PadRight` off-by-one write at exactly `maxLen`.

## Refactoring / duplication (shared-helper candidates)

The commands (`llcopy`/`llmove`/`lldel`, `llexec`/`llinfo`, `llcmp`/`llfind`) share a lot of boilerplate that's currently copy-pasted 2-3x, which is *why* several of the bugs above (`-o`/`-O` gate, retry-with-mkdir, `srcAttributes` typo) diverged between files:

- **Copy/Move**: decide-action+colorize+confirm block, the retry-with-mkdir-on-`ERROR_PATH_NOT_FOUND` loop, `-c` chmod parse+apply, keyboard-pause handling, and end-of-run stats printing are near-verbatim duplicated between `llcopy.cpp` and `llmove.cpp` — pull into `LLBase` helpers.
- **llexec/llinfo/llfind/llreplace/etc.**: the "parse options → scan → print errors/ignored/exit-test summary" `Run()` boilerplate recurs almost verbatim across nearly every command file — one `LLBase::ReportRunStats()`/`ReportExitTest()` would remove hundreds of duplicated lines.
- **llsupport.cpp** (the shared grab-bag, so this matters most): `ParseNum<uint/long/longlong>` are copy-pasted 3x (and share the same silent-failure-on-bad-input bug); `ParseList/ParseAttributes/ParseString` share an identical "require `=`, else error" skeleton; `ParseSizeOp/ParseTimeOp/ParseExitOp` reimplement the same comparison-operator switch 3x; `AppendFile/CopyFollowFile/OverWriteFile` all reimplement the same read/write/progress-callback copy loop.
- **dirscan/lldirSort**: two independent wildcard-matching engines that must be fixed twice; `FillEntry*`/`FillFindData*` sextet differs only by which FILETIME field is primary; six `...Dec` comparators are all just `-Inc(...)`.
- **llcmp**: manual `sprintf(..., "%s\\%s", ...)` path-joining repeated 6+ times instead of using the existing `LLPath::Join`; size-delta/percent-change formatting duplicated between `CompareFileSpecs`/`ReportCompareFileSpecs`.
- **lldir**: `ShowAttributes`/`ShowAttributeAsChar` both walk the same 15 flags in parallel if-chains — should be one table; full-path-building duplicated between `GetSoftLink`/`ShowAlternateDataStreams`.
- `FileSectors.cpp` appears to be entirely dead/orphaned code (references dozens of undefined globals from what looks like an unrelated GUI defragmenter) and isn't in the `.vcxproj` — candidate for deletion.
